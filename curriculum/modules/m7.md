# m7 — WAL, Replication, Vacuum & High Availability (build plan)

PGlite facts that shape this module (measured, PGlite 0.5.16 = PostgreSQL 18.6):
`wal_level = replica`, `fsync = off`, `data_checksums = on`, `full_page_writes = on` (cannot be changed), `wal_compression` accepts only `pglz`.
No checkpointer/WAL writer/autovacuum processes run (single "standalone backend"), so nothing vacuums or flushes behind the reader's back.
`pg_get_wal_records_info` reads only flushed WAL, so marks are taken with `pg_current_wal_insert_lsn()` and read up to `pg_current_wal_lsn()` after a commit.
Cumulative stats need `SELECT pg_stat_force_next_flush();` as its own statement before reading `pg_stat_user_tables`.
Logical slots fail ("logical decoding requires wal_level >= logical"); publications, physical slots, `pg_logical_emit_message`, `pg_backup_start/stop`, `pg_create_restore_point`, `pg_switch_wal` all work.
VACUUM VERBOSE output arrives as notices that the playground does not display, so presets read results from `pg_class`, `pg_visibility_map`, `pg_freespace`, `pg_stat_user_tables`.

## 1. wal-lsn — Write-ahead logging and LSNs
Facts
1. WAL rule: data-file changes may be written only after the WAL records describing them are flushed (wal-intro.html).
2. Only the WAL must be flushed at commit; it is sequential, and one flush can commit many transactions (group commit) (wal-intro.html, wal-configuration.html).
3. LSN = byte position in the WAL stream, type `pg_lsn`; subtracting two LSNs gives bytes (wal-internals.html, datatype-pg-lsn.html).
4. Segment files are 16 MB, pages 8 kB; names are 24 hex digits: timeline + segment number (wal-internals.html).
5. Each record has a resource manager (Heap, Btree, Transaction, XLOG…) and a CRC-32C (wal-reliability.html, pgwalinspect.html).
6. `wal_level` minimal < replica (default) < logical; changing it needs a restart (runtime-config-wal.html).
7. `synchronous_commit` levels off/local/remote_write/on/remote_apply; with no sync standbys only on/off differ (runtime-config-wal.html).
8. Async commit risks loss of the last transactions, never corruption; window up to 3 × `wal_writer_delay` (200 ms) (wal-async-commit.html).
9. `commit_delay` (0) and `commit_siblings` (5) widen the group-commit window (wal-configuration.html).
10. Rolled-back transactions still write WAL plus an ABORT record (measured).
Visualizer: Stepper over a captured run (INSERT, HOT UPDATE, DELETE, ROLLBACK, async INSERT). LSN tape with records sized by bytes; insert / write / flush pointers; click a record to decode its LSN into segment file name + offset.
Playground: `accounts` (50 rows, fillfactor 90) + `marks(label, lsn)`. Presets: current LSN and file name; one INSERT's records; UPDATE/DELETE/ROLLBACK records; LSN arithmetic; async commit at-risk bytes; WAL stats by rmgr.
Production: event-ingest service using `SET LOCAL synchronous_commit = off` for telemetry, kept on for payments.
Pitfalls: `fsync = off` confused with async commit; WAL on a full disk PANICs; misreading LSN differences across `pg_current_wal_lsn` vs insert LSN.

## 2. checkpoints-fpw — Checkpoints and full page writes
Facts
1. Checkpoint = all dirty pages flushed + checkpoint record; recovery starts at its redo point (wal-configuration.html).
2. Triggers: `checkpoint_timeout` 5 min or `max_wal_size` 1 GB (soft), whichever first; skipped if no WAL (wal-configuration.html).
3. `checkpoint_completion_target` 0.9 spreads writes; `checkpoint_warning` 30 s (runtime-config-wal.html).
4. Torn pages: 8 kB page = 16 × 512 B sectors; FPI on first modification after a checkpoint (wal-reliability.html).
5. With checksums on, even a hint-bit-only change logs an FPI (`FPI_FOR_HINT`) (runtime-config-wal.html wal_log_hints).
6. `wal_compression` compresses FPIs (pglz/lz4/zstd) (runtime-config-wal.html).
7. pg_control stores the latest checkpoint location; recovery reads pg_control → checkpoint record → redo forward (wal-internals.html).
8. Segments before the redo segment are recycled or removed; `min_wal_size` 80 MB (wal-configuration.html).
9. Standbys perform restartpoints at checkpoint records (wal-configuration.html).
Measured: after CHECKPOINT one HOT UPDATE wrote 14,830 B (heap FPI 6,560 + VM FPI 8,192); the next UPDATE on the same page 77 B; another page 6,633 B. pglz: heap image 4,154 B. Full-table update of 54 pages: 637 kB right after a checkpoint vs 326 kB the second time.
Visualizer: Stepper: checkpoint cycle on a timeline + buffer grid + WAL tape; crash and replay; Segmented `wal_compression` off/pglz changes FPI sizes.
Playground: `sensors` 2000 rows; presets: pg_control_checkpoint; FPI after CHECKPOINT; same page again; pglz; full-table update twice; pg_stat_wal.
Production: IoT platform where `checkpoint_timeout` 5 min caused WAL spikes; raise to 15 min + max_wal_size.
Pitfalls: frequent checkpoints (warning), `full_page_writes = off` on non-atomic storage, completion target 1.0.

## 3. vacuum — VACUUM vs VACUUM FULL
Facts
1. Four reasons to vacuum: space, stats, VM, wraparound (routine-vacuuming.html).
2. Plain VACUUM takes SHARE UPDATE EXCLUSIVE; FULL takes ACCESS EXCLUSIVE and writes a new file (routine-vacuuming.html, sql-vacuum.html).
3. Phases: initializing, scanning heap, vacuuming indexes, vacuuming heap, cleaning up indexes, truncating heap, performing final cleanup (progress-reporting.html).
4. Index passes repeat when dead TIDs exceed `maintenance_work_mem` / `autovacuum_work_mem` (progress-reporting.html).
5. Pruning (on access) removes HOT-dead tuples within a page without index work (storage-hot.html).
6. Truncation of empty tail pages needs a brief ACCESS EXCLUSIVE; `vacuum_truncate` / `TRUNCATE false` (sql-vacuum.html).
7. VACUUM sets VM bits and updates the FSM (storage-vm.html, storage-fsm.html).
8. VACUUM FULL progress shows in pg_stat_progress_cluster (progress-reporting.html).
9. `INDEX_CLEANUP`, `PARALLEL`, `SKIP_LOCKED`, `BUFFER_USAGE_LIMIT` options (sql-vacuum.html).
10. Cannot run inside a transaction block (sql-vacuum.html).
Measured: 106 pages, 2500 HOT updates + 1500 deletes at the tail; VACUUM: 1500 dead item identifiers on 17 pages, index scans 1, "truncated 106 to 90 pages", 106 set all-visible, 16 all-frozen; FULL: new relfilenode, pkey 30 → 26 pages.
Visualizer: page grid of 106 heap pages; Segmented VACUUM / VACUUM FULL; Stepper through phases with dead-TID store bar, index panels, VM bits, FSM.
Playground: `orders` fillfactor 70; presets: stats, pg_visibility, vacuum + check, freespace, VACUUM FULL relfilenode.
Production: SaaS audit table bloat; DELETE + VACUUM + partitioning or pg_repack instead of nightly FULL.
Pitfalls: VACUUM FULL in business hours, long transactions block cleanup, expecting space back.

## 4. autovacuum-tuning — Tuning autovacuum
Facts: thresholds `50 + 0.2·reltuples` capped at `autovacuum_vacuum_max_threshold` 100 M (new in 18); insert trigger `1000 + 0.2·reltuples·(1 − relallfrozen/relpages)`; analyze `50 + 0.1·reltuples`; naptime 1 min; 3 workers (`autovacuum_worker_slots` 16 in 18); cost delay 2 ms, limit 200 (from vacuum_cost_limit), page hit 1 / miss 2 / dirty 20; cost limit shared among workers; per-table storage parameters; autovacuum cancels on conflicting lock except anti-wraparound; no auto-ANALYZE of partitioned parents; stats from `track_counts` (routine-vacuuming.html, runtime-config-vacuum.html, runtime-config-autovacuum.html).
Visualizer: calculator (reltuples log slider, scale/threshold/cap, insert params, frozen %) + 24 h simulation of dead tuples with sawtooth autovacuum runs + cost-throttle MB/s.
Playground: `sessions` table with stats; presets compute the trigger from `pg_stat_user_tables` and `pg_class`, per-table reloptions, show settings.
Pitfalls: big tables never vacuumed under 0.2; disabled autovacuum; long transactions; frequent lock conflicts.

## 5. xid-wraparound — XID wraparound, freezing and MultiXacts
Facts: 32-bit XIDs compared modulo 2^32 (2 B past / 2 B future); special XIDs 0/1/2; freezing sets a flag; `vacuum_freeze_min_age` 50 M; `vacuum_freeze_table_age` 150 M (≤ 95% of max); `autovacuum_freeze_max_age` 200 M (runs even if autovacuum off, not cancelled); failsafe 1.6 B; warnings 40 M before wrap, stop at 3 M; `relfrozenxid`/`datfrozenxid`; multixacts in xmax, 400 M max age, members area 10 GB/20 GB; recovery steps (no single-user mode, no VACUUM FULL/FREEZE) (routine-vacuuming.html, runtime-config-vacuum.html, transaction-id.html).
Visualizer: XID ring with current XID, relfrozenxid, horizon; slider for age; thresholds bands; toggle "frozen" tuple; "no freezing" mode showing a row vanish at age 2^31.
Playground: burn procedure (100k xids ≈ 0.2 s), age(relfrozenxid), VACUUM FREEZE, pg_visibility all_frozen, mxid_age.

## 8. partitioning — Declarative partitioning and pruning
Facts: range/list/hash; range upper bound exclusive; default partition; pruning at plan time / executor init (Subplans Removed) / run time (never executed); `enable_partition_pruning`; ATTACH (SHARE UPDATE EXCLUSIVE) with pre-built CHECK; DETACH CONCURRENTLY (not with a default partition — measured); unique keys must include partition key; partition-wise join/aggregate off by default; DROP vs DELETE (ddl-partitioning.html, runtime-config-query.html).
Measured: DELETE one month = 1224 kB WAL, DROP partition = 4872 B.
Visualizer: query picker with real EXPLAIN output, partitions lit/pruned per stage, tuple routing.

## 10. connection-pooling — Connection pooling
Facts: one process per connection, `max_connections` 100, `superuser_reserved_connections` 3, idle-in-transaction holds snapshot, `idle_in_transaction_session_timeout`, `idle_session_timeout` warning about poolers, `transaction_timeout`, DISCARD ALL; PgBouncer modes (session/transaction/statement) are third-party behaviour (runtime-config-connection.html, runtime-config-client.html, sql-discard.html).
