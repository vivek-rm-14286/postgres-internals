# M1 — Foundations & Process Architecture (build plan)

PGlite facts captured for this module (PostgreSQL 18.6 in WASM, single process):
`pg_stat_activity` shows one row, `backend_type = 'standalone backend'`, pid 42. `shared_buffers` = 16384 × 8 kB (128 MB),
`wal_buffers` = 512 × 8 kB (4 MB, auto = 1/32 of shared_buffers), `transaction_buffers` = 32 (shared_buffers/512),
`io_method = sync`, `max_connections` = 100, `superuser_reserved_connections` = 3. `pg_shmem_allocations`: Buffer Blocks
134,221,824 B, Buffer Descriptors 1,048,576 B (64 B × 16384), XLOG Ctl 4,208,256 B, `transaction` SLRU 529,408 B,
`shared_memory_size` = 145MB. `pg_stat_io` lists 14 backend types including `io worker`, `slotsync worker`, `walsummarizer`.
Default `search_path` in PGlite is `public` (stock initdb: `"$user", public`), so presets set it explicitly.
A 20,000-row table (id, customer_id, md5 note) = 192 pages; first scan after eviction shows `shared read=192`, second `shared hit=192`;
each scan raises `usagecount` by one (2 → 3); CHECKPOINT clears `isdirty`.

## 1. what-is-postgres — What PostgreSQL is: cluster, client/server, a query's round trip

Facts
1. A **database cluster** is a collection of databases managed by one server instance; on disk it is one data directory (`PGDATA`). (creating-cluster.html)
2. After initdb a cluster holds `postgres`, `template1`, `template0`. (creating-cluster.html, manage-ag-templatedbs.html)
3. Hierarchy: cluster → database → schema → object. Roles, databases, tablespaces are cluster-wide (`pg_global`). (manage-ag-overview.html)
4. A connection reaches exactly one database; no cross-database queries in one connection. (manage-ag-overview.html)
5. Process per user: the postmaster listens (default port 5432, socket `/tmp/.s.PGSQL.5432`) and forks one backend per connection. (connect-estab.html, tutorial-arch.html)
6. The query text travels as plain text; the client does no parsing. (connect-estab.html)
7. Every message: 1 type byte + Int32 length (includes itself, not the type byte). The StartupMessage has no type byte. (protocol-overview.html)
8. libpq requests protocol 3.0 by default (196608); 3.2 is new in 18 with a variable-length cancel key. (protocol-overview.html)
9. Startup: StartupMessage → auth exchange → AuthenticationOk → ParameterStatus × n → BackendKeyData → ReadyForQuery('I'). (protocol-flow.html)
10. Simple query: Query('Q') → RowDescription('T') → DataRow('D')… → CommandComplete('C') → ReadyForQuery('Z'). Results are text format. (protocol-flow.html)
11. Multiple statements in one Query message run as one implicit transaction. (protocol-flow.html)
12. Backend stages: parse → rewrite → plan → execute. (query-path.html)
13. Each relation is a file `base/<database oid>/<relfilenode>`. (storage-file-layout.html)

Visualizer: Stepper "A query's round trip". Lanes: psql (libpq) | socket | postmaster | backend 4711 | data directory.
Steps 1–11 from TCP connect to Terminate. A wire log lists every message with type byte and length computed from the protocol
rules for the actual strings; clicking a message decodes its bytes. Proves: one fork per connection, text query, exact framing.

Playground: tutorial `weather`/`cities` tables. Presets: who/where am I; databases in the cluster; files on disk
(`pg_relation_filepath`); one statement = one transaction (xid per statement vs BEGIN…COMMIT); `statement_timestamp` vs `clock_timestamp`; protocol-level settings.

Production: connection-string mistakes (wrong database / socket path) → diagnose with `current_database()`, `inet_server_addr()`.
Pitfalls: expecting cross-database joins; DROP DATABASE while connected; trust auth after initdb; one statement vs implicit transaction.

## 2. process-model — The postmaster and one process per connection

Facts
1. Postmaster = first process; starts auxiliary processes, forks backends on demand. (glossary.html)
2. `max_connections` default 100, postmaster context; sizes shared memory. `superuser_reserved_connections` 3; `reserved_connections` 0 for `pg_use_reserved_connections`. (runtime-config-connection.html)
3. One semaphore per allowed connection/worker, in sets of 16 (+1 magic). (kernel-resources.html)
4. `pg_stat_activity`: one row per server process; `state` active / idle / idle in transaction / idle in transaction (aborted) / fastpath / disabled; `backend_type`. (monitoring-stats.html)
5. `authentication_timeout` 1 min. (runtime-config-connection.html)
6. Shutdown: SIGTERM smart, SIGINT fast, SIGQUIT immediate (children get SIGKILL after 5 s; WAL replay at next start). Never SIGKILL the postmaster. (server-shutdown.html)
7. A crashed backend makes the postmaster terminate all others and reinitialize (`restart_after_crash`, default on). (runtime-config-error-handling.html, kernel-resources.html)
8. OOM killer can kill the postmaster; protect with `oom_score_adj` -1000 + `PG_OOM_ADJUST_FILE`. (kernel-resources.html)
9. `pg_cancel_backend` / `pg_terminate_backend`; cancel uses a separate connection carrying PID + secret key. (functions-admin.html, protocol-flow.html)
10. `postmaster.pid` prevents two instances on one data directory. (server-start.html)
11. Backend memory is private (`pg_backend_memory_contexts`). (view-pg-backend-memory-contexts.html)

Visualizer: live process tree. Buttons: connect client, connect superuser, run query, BEGIN (idle in transaction), disconnect,
kill -9 a backend (crash restart), shutdown smart/fast/immediate. `max_connections` = 6, reserved 1 to show the FATALs.
Live `pg_stat_activity` table under the tree.

Playground: `pg_stat_activity`, `application_name`, backend types from `pg_stat_io`, GUC contexts, memory contexts, wait events.
Production: an API fleet with 40 pods × pool 20 = 800 connections; idle in transaction; fix with pooling and timeouts.
Pitfalls: raising max_connections to 2000; idle in transaction; kill -9; OOM killer.

## 3. shared-memory — Shared memory: buffers, WAL buffers and the commit log

Facts
1. `shared_buffers` default 128MB, postmaster; start at 25 % of RAM, rarely > 40 %. (runtime-config-resource.html)
2. Each buffer has a descriptor (tag, pin count, usage count, dirty flag); `pg_buffercache` exposes them; usage count 0..5. (pgbuffercache.html)
3. Clock sweep: pinned buffers are skipped, usage count is decremented, the first unpinned buffer at 0 is the victim. Dirty victims must be written (after WAL flush) before reuse.
4. Buffer access strategy rings for large seq scans, VACUUM (`vacuum_buffer_usage_limit` 2MB), COPY, CTAS. (glossary.html)
5. `wal_buffers` -1 → 1/32 of shared_buffers, between 64 kB and one WAL segment (16 MB). (runtime-config-wal.html)
6. SLRU caches: `transaction_buffers` (pg_xact), `subtransaction_buffers`, `multixact_*`, `notify_buffers`, `serializable_buffers`, `commit_timestamp_buffers`; `pg_stat_slru`. (runtime-config-resource.html, monitoring-stats.html)
7. pg_xact keeps 2 bits per transaction: in progress / committed / aborted / sub-committed. (storage-file-layout.html)
8. `pg_shmem_allocations` lists the main segment; DSM is separate. (view-pg-shmem-allocations.html)
9. Local memory: `work_mem` 4MB per sort/hash node, `hash_mem_multiplier` 2.0, `maintenance_work_mem` 64MB, `temp_buffers` 8MB. (runtime-config-resource.html)
10. Huge pages (`huge_pages = try`); `shared_memory_size_in_huge_pages`. (kernel-resources.html)

Visualizer: clock-sweep simulator: 16-buffer ring, clock hand, pins, usage counts, dirty flags; workloads hot set / seq scan
(with ring toggle); bgwriter pass; checkpoint. Stats tiles: hits, misses, evictions, backend writes. Shared memory map with real sizes.
Playground: pg_buffercache on a 192-page table: read → hit → usagecount → dirty → checkpoint → evict.
Production: nightly report scan evicting the hot set; ring buffers / pg_prewarm / sizing.
Pitfalls: shared_buffers 80 % of RAM; work_mem × nodes × connections; hit ratio misread; transparent huge pages.

## 4. background-processes — The background crew

Facts
1. Auxiliary processes: autovacuum launcher, bgwriter, checkpointer, logger, startup, archiver, walreceiver, walsummarizer, walwriter. (glossary.html)
2. bgwriter: `bgwriter_delay` 200ms, `bgwriter_lru_maxpages` 100, `bgwriter_lru_multiplier` 2.0. (runtime-config-resource.html)
3. checkpointer: `checkpoint_timeout` 5min, `max_wal_size` 1GB, `checkpoint_completion_target` 0.9. (wal-configuration.html)
4. walwriter: `wal_writer_delay` 200ms; async commit loss window up to 3 × delay. (wal-async-commit.html)
5. autovacuum launcher: `autovacuum_naptime` 1min, `autovacuum_max_workers` 3; threshold 50 + 0.2 × reltuples. (routine-vacuuming.html)
6. Cumulative stats live in shared memory, flushed by each process at most once per second; written to `pg_stat` on clean shutdown. (monitoring-stats.html)
7. archiver runs `archive_command` / `archive_library` per completed segment. (continuous-archiving.html)
8. PG18 AIO: `io_method` worker (default) / io_uring / sync; `io_workers` 3; `pg_aios`. (runtime-config-resource.html, view-pg-aios.html)
9. `pg_stat_bgwriter`, `pg_stat_checkpointer`, `pg_stat_io` (backend_type × object × context). (monitoring-stats.html)
10. logical replication launcher starts apply workers for subscriptions. (logical-replication-architecture.html)

Visualizer: Stepper over a process/memory/disk diagram: UPDATE dirties a page and writes WAL → COMMIT flush → walwriter →
bgwriter round → io workers read ahead → stats flush → autovacuum → checkpoint (spread, fsync, checkpoint record) → archiver.
Each step shows the governing GUC.
Playground: settings, pg_stat_io by backend type, pg_stat_bgwriter/checkpointer, autovacuum threshold per table, pg_stat_wal.
Production: checkpoint spikes from `max_wal_size` too small → `num_requested` vs `num_timed`.
Pitfalls: disabling autovacuum; checkpoints too frequent; backends doing their own writes; failing archive_command filling pg_wal.

## 5. databases-schemas-roles — Databases, schemas, search_path and roles

Facts
1. CREATE DATABASE copies `template1` by default; template0 for new encoding/locale; no other sessions on the source. (manage-ag-templatedbs.html)
2. Database-level GRANTs are not copied. `datallowconn` false on template0. (manage-ag-templatedbs.html)
3. search_path default `"$user", public`; first match wins; first existing schema is the creation target. (ddl-schemas.html)
4. pg_catalog searched implicitly first unless listed; pg_temp first for relations. (ddl-schemas.html, runtime-config-client.html)
5. Schemas you lack USAGE on are silently skipped (`current_schemas`). (verified in PGlite)
6. PG15+: PUBLIC lacks CREATE on public; public owned by `pg_database_owner`. (ddl-schemas.html, predefined-roles.html)
7. Roles are cluster-wide; CREATE USER = CREATE ROLE … LOGIN. (database-roles.html)
8. Membership options INHERIT / SET / ADMIN; LOGIN, SUPERUSER, CREATEDB, CREATEROLE never inherited. (role-membership.html)
9. Predefined roles: pg_read_all_data, pg_monitor, pg_signal_backend, pg_maintain… (predefined-roles.html)
10. pg_hba.conf: first matching line wins, no fall-through, no match = reject. `pg_hba_file_rules`. (auth-pg-hba-conf.html)
11. Default PUBLIC privileges: CONNECT/TEMP on databases, EXECUTE on functions, USAGE on types/languages. (ddl-priv.html)

Visualizer: three modes — search_path resolver (role, path, name; animated walk with skip reasons), pg_hba first-match
(client attempt vs rules), role graph (joe/admin/wheel/island from the docs).
Playground: try() helper returning SQLSTATE; roles, schemas, GRANT USAGE, SET ROLE, current_schemas, pg_hba_file_rules.
Production: multi-tenant schema-per-tenant with `ALTER ROLE … SET search_path`; read-only reporting role via pg_read_all_data.
Pitfalls: CREATE on public in upgraded DBs; search_path hijack in SECURITY DEFINER; hba order; DROP ROLE with owned objects.

## 6. normalization-constraints — Modelling data: normalization and constraints

Facts
1. CHECK passes on true or NULL. (ddl-constraints.html)
2. NOT NULL; at most one explicit not-null constraint per column; named NOT NULL in 18 (`contype = 'n'`). (ddl-constraints.html)
3. UNIQUE builds a unique B-tree; NULLs distinct unless `NULLS NOT DISTINCT`. (ddl-constraints.html)
4. PRIMARY KEY = UNIQUE + NOT NULL, one per table. (ddl-constraints.html)
5. FK actions NO ACTION (default, deferrable) / RESTRICT / CASCADE / SET NULL / SET DEFAULT; referencing columns not indexed automatically. (ddl-constraints.html)
6. DEFERRABLE only for UNIQUE, PK, EXCLUDE, FK. (sql-createtable.html)
7. EXCLUDE USING gist. Temporal keys `WITHOUT OVERLAPS` (18) → GiST, 23P01. (sql-createtable.html)
8. Generated columns: VIRTUAL default in 18, STORED; immutable functions only. (ddl-generated-columns.html)
9. Identity columns ALWAYS / BY DEFAULT; NOT NULL but not unique automatically. (ddl-identity-columns.html)
10. NOT ENFORCED for CHECK and FK (18). (sql-createtable.html)

Visualizer: normalization stepper: messy order sheet (0NF) → 1NF → anomalies → 2NF → 3NF → constraints. Columns animate
between tables with layoutId; functional dependency colouring.
Playground: the 3NF schema with try() to show each constraint's SQLSTATE; generated virtual column; temporal key.
Production: an e-commerce order table with denormalized customer data drifting; split + FK + backfill.
Pitfalls: unindexed FK; CHECK with NULL; UNIQUE with NULLs; NOT ENFORCED lying to the planner.
