## 1. views-matviews — Views and materialized views
Facts
1. A view is a relation with no storage (`relkind = 'v'`, `relfilenode = 0`) plus an `ON SELECT DO INSTEAD` rule named `_RETURN` in `pg_rewrite` (rules-views).
2. The rewriter replaces the view's range-table entry with a subquery holding the rule's stored query tree, then recurses into it (rules-views).
3. Expansion happens before planning, so the planner pulls the subquery up and sees one flat join (rules-views). PGlite: view and hand-written subquery give the same plan, `Hash Join cost=8.32..12.86`, index scan on `orders_pkey`.
4. Privileges on base tables are checked as the view owner unless `security_invoker = true` (sql-createview, rules-privileges).
5. Views hide columns reliably but not rows; `security_barrier` stops cheap user functions running before the view's quals (rules-privileges).
6. Auto-updatable: one FROM item, no WITH/DISTINCT/GROUP BY/HAVING/LIMIT/OFFSET/set ops, no aggregates/window/SRF in the select list (sql-createview).
7. `WITH CHECK OPTION` rejects INSERT/UPDATE rows the view could not see; CASCADED is the default (sql-createview).
8. `SELECT *` in a view is expanded at creation; later table columns do not appear (sql-createview).
9. A materialized view stores rows (`relkind = 'm'`); the rule is used only to populate it (rules-materializedviews).
10. REFRESH replaces contents; plain REFRESH blocks readers; CONCURRENTLY needs a populated matview and a unique, non-partial, column-only index (sql-refreshmaterializedview).
11. `WITH NO DATA` leaves the matview unscannable until refreshed (sql-creatematerializedview).
Visualizer: Segmented view/matview. View mode: Stepper over the query tree (parse, find `_RETURN`, substitute subquery RTE, recurse, planner pull-up, final plan with real costs). Matview mode: Stepper over CREATE (stored heap, relfilenode), SELECT (seq scan of stored rows), base table change (stale), REFRESH (new relfilenode, ACCESS EXCLUSIVE), REFRESH CONCURRENTLY (diff by unique key, EXCLUSIVE, same relfilenode).
Playground: products/orders (200/20k rows), view `order_lines`, matview `daily_revenue`. Presets: pg_rewrite row; view EXPLAIN vs subquery; matview + stale data; CONCURRENTLY fails then works with unique index; relfilenode before/after refresh; WITH CHECK OPTION via try_sql; updatability in information_schema.
Production: dashboard aggregate recomputed on every page load → matview + unique index + REFRESH CONCURRENTLY on a schedule.
Pitfalls: CONCURRENTLY without unique index; SELECT * frozen columns; leaky view without security_barrier; dropping a column used by a view.

## 2. triggers — Triggers
Facts
1. Trigger functions take no args and return `trigger`; not writable in plain SQL (triggers).
2. Matrix: BEFORE/AFTER ROW on tables and foreign tables; INSTEAD OF ROW on views only; TRUNCATE statement-only; default is FOR EACH STATEMENT (sql-createtrigger).
3. Statement triggers fire once even for zero rows (triggers). PGlite: `UPDATE … WHERE false` fires BEFORE and AFTER STATEMENT.
4. Same-event triggers fire alphabetically by name (triggers).
5. BEFORE ROW returning NULL skips the row and later triggers for it; the returned row replaces NEW (triggers).
6. Row AFTER triggers are queued and fire at the end of the statement, before AFTER STATEMENT (triggers).
7. AFTER trigger WHEN is evaluated right after the row change and decides whether an event is queued (sql-createtrigger).
8. Transition tables: `REFERENCING OLD TABLE … NEW TABLE …`, AFTER only, no column list, single event (sql-createtrigger).
9. BEFORE ROW sees rows processed earlier in the same statement; AFTER ROW sees all changes (trigger-datachanges).
10. Constraint triggers are AFTER ROW and can be deferred to commit (sql-createtrigger).
11. Event triggers: `login`, `ddl_command_start`, `ddl_command_end`, `table_rewrite`, `sql_drop` (event-triggers).
12. No cascade depth limit; recursion is the programmer's problem; `pg_trigger_depth()` helps (triggers).
PGlite firing log for `UPDATE inventory SET qty = qty - 5` over 3 rows (B-2 goes negative): a_before_stmt; b_touch A-1; c_guard A-1 ok; b_touch B-2; c_guard B-2 skipped; b_touch C-3; c_guard C-3 ok; d_audit A-1; d_audit C-3; e_summary old_rows=2 new_rows=2 delta=-10.
Visualizer: timeline with lanes (statement, per-row BEFORE, AFTER queue, transition tables), steps generated from toggles: guard on/off, WHEN on/off, rename b_touch to z_touch (alphabetical order flips).
Playground: inventory + trigger_log + the five triggers. Presets: firing log; zero-row statement; no-op update and WHEN; pg_trigger catalog; INSTEAD OF trigger on a view; recursion guard with pg_trigger_depth.
Production: audit trail per row vs one statement trigger with transition tables.
Pitfalls: AFTER ROW trigger updating same table (recursion); BEFORE trigger returning NULL by accident; heavy work in row triggers on bulk loads; relying on creation order.

## 3. plpgsql — PL/pgSQL functions and procedures
Facts
1. Body is a block: `[DECLARE] BEGIN … [EXCEPTION …] END` (plpgsql-structure).
2. First call compiles to an instruction tree; each SQL statement is prepared on first execution via SPI and may get a cached generic plan (plpgsql-implementation).
3. Errors in unvisited code paths surface only when reached (plpgsql-implementation).
4. A block with EXCEPTION is a subtransaction; on error, DB changes inside it roll back but local variables keep their values (plpgsql-control-structures). PGlite: top xid 753, failing block used 754 (aborted), second block 755.
5. EXCEPTION blocks are much more expensive to enter and exit (plpgsql-control-structures). PGlite: 200k loop iterations 17.9 ms plain vs 136.6 ms with an EXCEPTION block.
6. `OTHERS` does not catch `QUERY_CANCELED` or `ASSERT_FAILURE` (plpgsql-control-structures).
7. `RETURN NEXT` / `RETURN QUERY` append to the result set; the function returns at the final RETURN (plpgsql-control-structures).
8. EXECUTE runs dynamic SQL, planned each time; use `format('%I', …)`, `%L`, or `USING` to avoid injection (plpgsql-statements).
9. Procedures called with CALL (and DO) may COMMIT/ROLLBACK; not inside a block with EXCEPTION, not under a SELECT (plpgsql-transactions).
10. Volatility: VOLATILE re-evaluated each row and sees fresh snapshot per query; STABLE/IMMUTABLE use the caller's snapshot and never see the calling command's changes (xfunc-volatility).
11. `'now'` literal in a typed context is frozen at first analysis (plpgsql-implementation).
Visualizer: code panel with a moving cursor, transaction stack (top xid / subxact xids), audit rows with xmin and status, local variables; toggle "with EXCEPTION / without". Cost tiles with measured timing.
Playground: accounts/audit + demo() function. Presets: run demo, xmin of rows, cost of EXCEPTION loop, procedure with COMMIT, dynamic SQL with format, volatility catalog.
Pitfalls: EXCEPTION inside hot loops; SQL injection with string concat; variable/column name conflict; IMMUTABLE lies in indexes.

## 4. rule-system — The rule system
Facts
1. Rewriter sits between parser and planner and turns one query tree into zero or more (rules).
2. Query tree parts: command type, range table, result relation, target list, qual, join tree (querytree).
3. Non-SELECT rules: ALSO (default) or INSTEAD, optional qual, NEW/OLD, multiple actions; they create new trees (rules-update).
4. Qualified ALSO rule → action tree with rule qual AND original qual, plus the original (rules-update).
5. log_shoelace rewrite: merge range table, add rule qual, add original qual, replace NEW with target-list entries, replace OLD with result relation (rules-update). PGlite EXPLAIN shows `Filter: (6 <> sl_avail)`.
6. ON INSERT: original runs first; ON UPDATE/DELETE: original runs after the actions (rules-update).
7. If NEW column is not in the target list it means OLD (UPDATE): `SET sl_color = 'green'` writes no log (rules-update).
8. Multi-row UPDATE logs with one INSERT … SELECT: 4 rows updated, 3 logged (rules-update). PGlite confirms.
9. Rules are applied in alphabetical order; command status comes from the last INSTEAD query of the same type (rules-status).
10. Volatile functions in NEW can run more than once: serial default evaluated twice (rules-update). PGlite: events ids 1,2 vs copy 3,4.
11. Rules cannot enforce FKs or raise errors; triggers usually better (rules-triggers).
Visualizer: Stepper of the five steps with query-tree cards, Segmented scenario: sl_avail=6, sl_color only, multi-row.
Playground: shoelace schema from the docs. Presets: pg_rewrite, EXPLAIN two plans, log results, no-op color update, multi-row, volatile nextval pitfall, DO INSTEAD NOTHING on a view.
Pitfalls: nextval double evaluation; silent INSTEAD NOTHING; WITH not supported; rules vs RETURNING/COPY.

## 5. fdw — Foreign data wrappers
Facts
1. SQL/MED objects: wrapper (handler + validator) → server → user mapping → foreign table (ddl-foreign-data, postgres-fdw).
2. Handler returns an `FdwRoutine` of C callbacks; scan callbacks required (fdwhandler).
3. Without a validator, options are not checked (fdw-functions).
4. Planning: GetForeignRelSize → GetForeignPaths → GetForeignPlan; executor Begin/Iterate/ReScan/End (fdw-callbacks).
5. postgres_fdw ships WHERE clauses only with built-in (or listed extension) and IMMUTABLE functions/operators (postgres-fdw).
6. Joins ship when both tables are on the same server and user mapping; aggregates, sorts and LIMIT can ship too (postgres-fdw, fdw-planning).
7. Remote transactions use REPEATABLE READ (SERIALIZABLE if local is), no 2PC (postgres-fdw).
8. `fetch_size` default 100, `batch_size` default 1, `fdw_startup_cost` 100, `fdw_tuple_cost` 0.2, `use_remote_estimate` false (postgres-fdw).
9. Remote session runs with `search_path = pg_catalog`, `TimeZone = UTC` (postgres-fdw).
10. `EXPLAIN VERBOSE` shows the Remote SQL (postgres-fdw).
11. file_fdw reads server files via COPY, read-only, options on the table only (file-fdw).
12. `IMPORT FOREIGN SCHEMA` creates foreign tables from the remote catalog (sql-importforeignschema).
PGlite: no file_fdw/postgres_fdw. Wrapper without handler can be created; querying raises `foreign-data wrapper "…" has no handler`.
Visualizer: interactive pushdown planner (checkbox quals, ORDER BY, LIMIT, aggregate, join), output Remote SQL, local Filter, simulated rows over the wire (illustrative remote table of 1,000,000 rows).
Playground: wrapper/server/user mapping/foreign tables catalog objects; provolatile check; try_sql shows the no-handler error.
Pitfalls: now() not shipped; collation/type mismatch; READ COMMITTED surprise; N+1 fetches with small fetch_size.

## 6. extensions — Extensions everyone runs
Facts
1. Extension = control file + `name--version.sql` scripts (+ shared library) (extend-extensions).
2. Member objects are tracked in pg_depend with deptype 'e'; DROP EXTENSION removes them; pg_dump emits only CREATE EXTENSION (extend-extensions). PGlite: pg_trgm 1.6 has 47 member objects.
3. Updates follow the shortest chain of `old--new.sql` scripts; `pg_extension_update_paths` (extend-extensions).
4. `trusted = true` lets non-superusers with CREATE on the database install (pg_trgm, pgcrypto trusted; pg_stat_statements, pageinspect not) (extend-extensions, contrib).
5. pg_stat_statements needs shared_preload_libraries and compute_query_id; one row per dbid/userid/queryid/toplevel (pgstatstatements).
6. Trigram: words padded with two leading spaces and one trailing; similarity = shared / union; threshold 0.3 (pgtrgm). PGlite: similarity('postgres','postgis') = 0.416667.
7. gin_trgm_ops / gist_trgm_ops support LIKE/ILIKE/~ with unanchored patterns; KNN `<->` only with GiST (pgtrgm).
8. pgvector: `vector(n)`, operators `<->` L2, `<=>` cosine, `<#>` negative inner product; HNSW (m=16, ef_construction=64 defaults) and IVFFlat; `hnsw.ef_search` default 40; approximate results.
9. pageinspect, pgcrypto (digest, crypt/gen_salt), pg_buffercache, auto_explain (O-contrib).
Visualizer: tabs: pg_trgm (type two strings, live trigram sets, overlap, similarity, threshold) and HNSW (stepper of a greedy layered search over a 2D graph).
Playground: extensions pg_trgm, vector, pg_stat_statements, pgcrypto, pageinspect.
Pitfalls: pg_stat_statements not preloaded; trigram search on patterns shorter than 3 chars; HNSW recall vs filters; extension upgrades without ALTER EXTENSION UPDATE.

## 7. full-text-search — Full-text search
Facts
1. Parser tokenizes and classifies; dictionaries normalize to lexemes and drop stop words; tsvector = sorted lexemes with positions (textsearch-intro).
2. Stop words are dropped but still consume positions (textsearch-dictionaries).
3. `'…'::tsvector` does not normalize; `to_tsvector` does (textsearch-intro). PGlite: cast match false, function match true.
4. websearch_to_tsquery: quotes → `<->`, `or` → `|`, `-` → `!`, never errors (textsearch-controls).
5. Expression GIN index needs the 2-argument `to_tsvector` (textsearch-tables).
6. Generated stored tsvector column is the modern pattern (textsearch-tables).
7. GIN: one entry per lexeme with a posting list; GiST: lossy signature, recheck (textsearch-indexes).
8. ts_rank / ts_rank_cd, weights A–D default {0.1, 0.2, 0.4, 1.0} (textsearch-controls).
9. ts_headline uses the original document and is slow; output not XSS-safe (textsearch-controls).
10. Limits: lexeme < 2 KB, 256 positions per lexeme, positions ≤ 16383, tsvector < 1 MB (textsearch-limitations).
Visualizer: 6 docs captured from PGlite: pick doc → token → dictionary → lexeme pipeline; pick query → tsquery → GIN entry lookup → posting lists combined → matches + rank.
Playground: docs with generated tsv and GIN index.
Pitfalls: index not used due to config mismatch; casting text to tsvector; ranking cost over many matches; english stemming of names.

## 8. row-level-security — Row-level security
Facts
1. ENABLE RLS with no policy = default deny; owner bypasses unless FORCE; superusers and BYPASSRLS always bypass (ddl-rowsecurity).
2. Permissive policies OR together; restrictive AND; at least one permissive needed for any access (ddl-rowsecurity, sql-createpolicy).
3. USING filters existing rows silently; WITH CHECK errors on new rows (sql-createpolicy).
4. FOR ALL/UPDATE with no WITH CHECK reuse USING (sql-createpolicy).
5. Policies are applied before user quals except leakproof ones (ddl-rowsecurity). PGlite plan: `Filter: ((status <> 'archived') AND (tenant_id = …) AND (title ~~ 'L%'))`.
6. `row_security = off` makes filtered queries error instead of bypassing (ddl-rowsecurity). PGlite: `query would be affected by row-level security policy`.
7. FK/unique checks bypass RLS → covert channel (ddl-rowsecurity).
8. Views run with owner privileges unless security_invoker (sql-createview).
9. Policy enforcement for INSERT/UPDATE happens after BEFORE triggers (sql-createpolicy).
Visualizer: live policy combiner: rows table, toggle policies (permissive/restrictive), set role and session vars, see combined expression and filtered rows animate; INSERT check panel.
Playground: tickets, role app_user, policies with current_setting.
Pitfalls: testing as superuser/owner; missing setting → error vs NULL; leaking through unique violations; restrictive-only policies deny all.
