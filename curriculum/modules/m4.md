## 1 query-pipeline — From SQL text to rows
Facts (docs: query-path, parser-stage, rule-system, planner-optimizer, executor, sql-prepare, runtime-config-query, geqo)
1. Five stages: connection → parser → rewriter → planner/optimizer → executor (query-path).
2. Raw parsing (`scan.l` lexer + `gram.y` bison grammar) uses only syntax rules and makes **no catalog lookups** (parser-stage).
3. Reason: catalog lookups need a transaction; raw parsing alone is enough to recognise BEGIN/ROLLBACK (parser-stage).
4. Parse analysis turns the raw tree into a **query tree**: resolves tables, columns, types; `FuncCall` → `FuncExpr` or `Aggref` (parser-stage).
5. The rewriter's input and output are both query trees; a view is a `_RETURN` rule expanded like a macro (rule-system).
6. The planner first builds cheap **paths**, one per way to scan each relation; a seq scan path always exists (planner-optimizer).
7. Join search is near-exhaustive dynamic programming below `geqo_threshold` (12 FROM items); GEQO above (runtime-config-query, geqo).
8. Three join methods: nested loop, merge join, hash join (planner-optimizer).
9. Executor is a **demand-pull** pipeline: each call returns one more row or NULL (executor).
10. PREPARE does parse+analyze+rewrite once; EXECUTE plans and runs (sql-prepare).
11. `plan_cache_mode = auto`: first 5 executions custom, then generic if its cost is not much higher than the custom average (sql-prepare).
Visualizer: Stepper conveyor over one real query (view `big_orders` joined to `customers`): text → tokens → raw parse tree → query tree (OIDs, types) → rewritten (view inlined) → paths with real costs (hash 2022.47, merge 2787.77, nested loop 3528.49) → plan tree → executor pull (rows climbing the tree). Second mode: plan cache timeline (by_cust switches to generic at execution 6; by_status stays custom).
Playground: customers/orders/view. Presets: raw vs analyzed errors (syntax vs unknown column), view rewrite in EXPLAIN VERBOSE, join methods via enable_*, PREPARE + pg_prepared_statements counts, EXPLAIN (GENERIC_PLAN).
Production: ORM prepared statement with skewed status flips to a bad generic plan → `plan_cache_mode = force_custom_plan` for that role.
Pitfalls: generic plan on skewed data; >12-table joins hit GEQO; views are not materialized; parse errors vs analysis errors.

## 2 cost-model — The cost model
Facts (runtime-config-query, using-explain, index-cost-estimation, sql-explain)
1. Costs are arbitrary units; `seq_page_cost = 1.0` is the unit. 2. Defaults: random_page_cost 4.0, cpu_tuple_cost 0.01, cpu_index_tuple_cost 0.005, cpu_operator_cost 0.0025, effective_cache_size 4GB.
3. Seq scan = pages × seq_page_cost + rows × cpu_tuple_cost (+ rows × cpu_operator_cost per qual). Real: 935 + 1000 = 1935; with filter 2185.
4. Startup vs total cost; LIMIT interpolates; EXISTS uses startup cost.
5. Index scan heap cost interpolates between correlated (sequential) and uncorrelated (random) by correlation².
6. `enable_*` flags only add a disable penalty; plans still form (`Disabled: true`).
7. effective_cache_size allocates nothing. 8. random_page_cost per tablespace. 9. Lower random_page_cost → index scans win more often.
Visualizer: real PGlite cost grid (2 tables × 10 random_page_cost values × 3 plan types × 19 selectivities). Sliders for selectivity and random_page_cost, toggle correlated vs scattered column; curves of seq/index/bitmap cost with crossover; live seq-scan formula.
Pitfalls: SSD left at 4.0; benchmarking enable_seqscan=off; comparing costs across queries.

## 3 statistics — Planner statistics
Facts (planner-stats, planner-stats-details, row-estimation-examples, view-pg-stats, sql-analyze, multivariate-statistics-examples, sql-createstatistics)
1. ANALYZE samples 300 × max target rows. 2. default_statistics_target 100 = max MCVs and histogram buckets. 3. n_distinct > 0 count, < 0 fraction, −1 unique.
4. `=` on an MCV: selectivity = its frequency. 5. Not an MCV: (1 − Σmcf − null_frac)/(n_distinct − #mcv).
6. `<`: Σ matching MCV freqs + histogram fraction × (1 − Σmcf). Histogram excludes MCVs; linear inside a bucket.
7. AND multiplies (independence). 8. Extended stats: dependencies, ndistinct, mcv; need ANALYZE after CREATE STATISTICS. 9. correlation feeds index cost.
Visualizer: real pg_stats for `trips.zone` (statistics target 10): MCV bars + histogram buckets; mode `=` / `<` / two columns; draggable constant shows formula and PostgreSQL's real estimate vs actual count. Extended-stats mode: 1 vs 100.
Pitfalls: stale stats after bulk load; correlated columns; n_distinct misestimates; expression index needs ANALYZE.

## 5 hash-index
Facts (hash-index, sql-createindex, pageinspect): 4-byte hash only; lossy; `=` only; no unique/multicolumn; metapage/bucket/overflow/bitmap pages; maxbucket/highmask/lowmask; one bucket split at a time, foreground; never shrinks; empty index starts with 8 buckets (maxbucket 7), ffactor 307 for int4 and split at ntuples > ffactor × (maxbucket+1) (real: 2457 rows → maxbucket 8).
Visualizer: live linear-hash sim with real `hashint4` codes, small pages; insert keys, insert duplicates (overflow chain), split animation.
Pitfalls: duplicates → overflow chains; growth spikes; expecting smaller than btree for small keys (uuid hash 1040 kB vs btree 632 kB at 20k rows).

## 6 gin
Facts (gin, sql-createindex, runtime-config-client): entry tree of keys; posting list vs posting tree; pending list with fastupdate (default on), gin_pending_list_limit 4MB, flush on VACUUM/autoanalyze/gin_clean_pending_list/limit; every search scans pending list; opclasses array_ops, jsonb_ops, jsonb_path_ops, tsvector_ops, pg_trgm; consistent/triConsistent with recheck; no index-only scans.
Visualizer: live sim: insert documents (tags) into pending list; flush merges into entry tree; posting list → posting tree at threshold; query `@>` intersects posting lists and scans pending list.
Pitfalls: flush spike; jsonb `->>` equality not indexable by GIN; slow bulk loads; pending list making reads slow.

## 7 gist-spgist
Facts (gist, spgist, indexes-types, ddl-constraints EXCLUDE): GiST balanced tree of predicates with consistent/union/penalty/picksplit/same; KNN via distance lower bounds; exclusion constraints; SP-GiST quad-tree/k-d/radix, unbalanced, non-overlapping partitions.
Visualizer: 2-D points; GiST R-tree with overlapping MBRs vs SP-GiST quad-tree partitions; step-through KNN best-first search with a priority queue of real distances.
Real: KNN LIMIT 5 on 50k points = 8 buffers (GiST), 14 (SP-GiST); sizes 3.3 MB vs 2.3 MB.

## 8 brin
