# E2 — Time-Series with TimescaleDB (plan)

Facts come from `research/W-timescaledb.md` (TimescaleDB 2.32.0 README, changelog, official docs) and the PostgreSQL 18
docs. TimescaleDB cannot run in PGlite: visualizers simulate it, playgrounds run the native PostgreSQL 18 equivalent,
production examples and pitfalls show real 2.32-era TimescaleDB SQL. Every playground number below was measured on
PGlite (PostgreSQL 18.6) with the exact lesson SQL.

Editions, stated in every lesson where relevant: **Apache 2 edition** (`timescaledb.license = 'apache'`; what Neon ships:
"Only Apache-2 licensed features are supported. Compression is not supported.") has hypertables, `show_chunks`,
`drop_chunks`, `add_dimension`, `time_bucket`, `first`, `last`, `histogram`. **Community edition** (Tiger Data License,
default `timescale`) adds the columnstore, continuous aggregates, retention policies, jobs (`add_job`),
`time_bucket_gapfill`/`locf`/`interpolate`, SkipScan. Tiering to object storage is Tiger Cloud only.

## 1. time-series-basics — Time-series data on PostgreSQL
Facts
1. Time-series rows arrive in time order, are rarely updated, are queried by time range and age out (W §4.1).
2. Rows inserted in time order make the heap physically sorted: `pg_stats.correlation` = 1 for `time` (brin.html, view-pg-stats.html).
3. BRIN stores min/max per block range (`pages_per_range`, default 128) (brin.html).
4. Measured: 200,000 rows (1/s) → heap 1274 pages / 10192 kB, 157 rows per page; BRIN (32 pages/range) 24 kB; B-tree 4408 kB.
5. A 1-hour query on BRIN: `Heap Blocks: lossy=32`, `Rows Removed by Index Recheck: 1424`, 3600 rows (one 32-page range).
6. Shuffled copy: correlation ≈ 0, the same query reads `lossy=1280` blocks and rechecks away 196,400 rows.
7. `date_bin(stride, ts, origin)` buckets timestamps (functions-datetime.html); no months; origin required.
8. Declarative partitioning gives chunk-like pruning and cheap retention, but no automatic partition creation (ddl-partitioning.html).
9. TimescaleDB is an extension that must be in `shared_preload_libraries`; current 2.32.0 supports PG 16–18 (W §2.1–2.2).
10. Editions and Neon limits (W §2.1, §2.11).
Visualizer: BRIN range map of the real 200k-row table (40 ranges × 32 pages). Drag the query window; the ranges whose min/max
overlap light up; stats tiles show lossy pages, rows rechecked, rows returned. Toggle "time-ordered" vs "shuffled".
Second panel: edition matrix (Apache / Community / Neon) lighting features.
Playground: `readings` 200k rows + BRIN. Presets: physical order & correlation; BRIN plan; B-tree vs BRIN size; hourly
`date_bin`; shuffled table; latest reading per sensor.
Production: IoT platform keeping 30 days of 1 Hz readings in a plain table; BRIN + daily partitions vs moving to TimescaleDB.
Pitfalls: BRIN on non-correlated column; DELETE-based retention bloat; `date_bin` month error; assuming Neon has compression.

## 2. hypertables-chunks — Hypertables and chunks
Facts: `CREATE TABLE … WITH (tsdb.hypertable, tsdb.partition_column, tsdb.chunk_interval)` since 2.20 (auto partition
column 2.23); default chunk interval 7 days; `create_hypertable(rel, by_range('time', INTERVAL '1 day'))`; chunks in
`_timescaledb_internal._hyper_<ht>_<chunk>_chunk`, created on demand; boundaries aligned from epoch 0;
`set_chunk_time_interval` affects only new chunks; sizing rule: indexes of active chunks within 25% of memory (64 GB:
2 GB/day → 7 days, 10 GB/day → 1 day); >1000 chunks is a warning sign; default index `time DESC`; UNIQUE must include the
time column; `add_dimension(by_hash)` multiplies chunks and is discouraged; ChunkAppend runtime exclusion.
Visualizer: live hypertable simulation. Buttons: ingest 6 h, late row, far-future row; Segmented chunk interval
(6 h / 1 day / 7 days) and hash partitions (1 / 2); drag a query window to see chunk exclusion; mode toggle TimescaleDB vs
native partitioning (ERROR no partition). Sizing calculator.
Playground: native partitioned `conditions` with an `ensure_chunk()` helper. Presets: chunk list; plan-time exclusion;
runtime exclusion (`Subplans Removed: 5`); no automatic chunk (`try_sql`), then ensure_chunk; unique key rule;
hash sub-partitioning; ordered append vs Merge Append.

## 3. time-bucket-gapfill — time_bucket and gap filling
Facts: `time_bucket(width, ts [, offset] [, origin] [, timezone])` returns bucket start; default origin 2000-01-03 (Monday)
below 1 month, 2000-01-01 for months; UTC alignment; timezone argument; `date_bin` equivalent but no months;
`time_bucket_gapfill` needs WHERE bounds, top-level only, Community; `locf`, `interpolate` Community; `first/last` Apache,
not index-assisted on rowstore; PG 18 has no `IGNORE NULLS`; `time_bucket_ng` removed 2.25.
Visualizer: mode "Bucketing" (72 h axis across the 2026-03-29 Berlin DST switch; width, origin, offset, timezone controls;
readings snap into buckets) and mode "Gap filling" (hourly bars 11, –, 20, –, –, 50; toggle plain / gapfill / locf /
interpolate → 11 15.5 20 30 40 50).
Playground: `metrics` sparse rows. Presets: date_bin = time_bucket; months; DST; gapfill; locf; interpolate; first/last.

## 4. continuous-aggregates — Continuous aggregates
Facts: materialization hypertable; refresh in two transactions; invalidation log stores min/max time per transaction;
writes newer than the invalidation threshold are not logged; policy `start_offset`, `end_offset`, `schedule_interval`;
only whole buckets in the window; real-time off by default since 2.13; backfill not visible until refresh;
`buckets_per_batch` default 10 (2.25); hierarchical since 2.9, multiple-of rule; avg of avgs is wrong; retention vs refresh window.
Visualizer: simulated hypertable hours 00–11, materialized buckets, watermark, invalidation log; buttons advance 1 h,
backfill, run policy, manual refresh, toggle real-time, one-vs-two transaction backfill.
Playground: matview vs incremental emulation (summary table, statement trigger log, refresh procedure, watermark, real-time view).

## 5. compression-columnstore — Compression and the columnstore
Facts: Hypercore = rowstore + columnstore (renamed from compression in 2.18); up to 1000 rows per batch per segmentby value;
per-batch min/max metadata; codecs (delta-of-delta + simple-8b + RLE before 2.32, AIC default in 2.32, Gorilla XOR floats,
dictionary); settings `segmentby`, `orderby`; policy `add_columnstore_policy(after =>)`; default schedule is documented
two ways (contradiction — never one number); DML decompresses only affected batches,
`max_tuples_decompressed_per_dml_transaction` 100000; "90%+" typical, demo 194 MB → 24 MB; Community only.
Visualizer: Stepper of 12 rows → segment → order → batch arrays → codecs → batch skipping → UPDATE decompresses one batch;
Segmented segmentby (device / none / reading_id).
Playground: `ticks` 30k rows: 1568 kB rowstore vs 216 kB arrays (30 batches); skipping; delta-of-delta; segmentby choices
(unique segmentby 4104 kB); updating one value rewrites the batch.

## 6. retention-jobs — Retention, tiering and jobs
Facts: `drop_chunks` drops whole chunks only; `add_retention_policy(drop_after)` one per hypertable; jobs scheduler,
`timescaledb_information.jobs/job_stats`; `add_job(proc, schedule_interval, config)`, `fixed_schedule` default true;
failure backoff; `max_background_workers` 16; cagg + retention interaction; tiering Tiger Cloud only; multi-node removed in 2.14.
Visualizer: lifecycle timeline (daily chunks, now advancing): rowstore → columnstore → tiered → dropped; sliders for
`drop_after`, columnstore `after`, cagg `start_offset`; warning when retention cuts into the refresh window; jobs table.
Playground: 10 daily partitions; DELETE WAL vs drop job; jobs registry + `run_due_jobs()` emulating the scheduler; failure backoff.
