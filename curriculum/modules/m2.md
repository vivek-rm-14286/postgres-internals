# Module 2 — Storage & Page Layout Internals (plan)

All numbers below were measured on PGlite (PostgreSQL 18.6, wasm32, MAXALIGN 8, 8 KB blocks) unless marked "docs".
Lesson 5 (`slotted-page`) is the finished reference lesson.

## 1. primitive-types — Primitive types, alignment and padding
Facts
- smallint 2 B, integer 4 B, bigint 8 B; out-of-range raises an error (datatype-numeric).
- numeric: 2 bytes per 4 decimal digits + 3–8 B overhead; exact; slow (datatype-numeric). Measured on disk: `1` → 5 B, `123456789` → 9 B.
- real 4 B / double 8 B IEEE 754; `0.1+0.2 = 0.3` is false for float8, true for numeric (datatype-numeric).
- numeric rounds ties away from zero, float to even: `round(2.5::numeric)`=3, `round(2.5::float8)`=2 (datatype-numeric).
- money 8 B, locale-dependent output via `lc_monetary` (datatype-money).
- text/varchar: 1-byte header up to 126 B, 4-byte header beyond; no speed difference between text/varchar/char(n) (datatype-character).
- boolean 1 B; date 4 B; timestamp/timestamptz 8 B; interval 16 B; uuid 16 B (datatype-*).
- `pg_type.typlen` / `typalign` (c=1, s=2, i=4, d=8) drive layout; each fixed column starts at a multiple of its alignment (storage-page-layout, catalog-pg-type).
- Short (1-byte header) varlenas are not aligned (storage-toast).
- Tuple header 23 B → `t_hoff` 24 (storage-page-layout). Row length is MAXALIGNed on the page, plus a 4-byte line pointer.
- Measured: `(bool, int8, int2, timestamptz, int4, text 'hello', bool)` = 67 B; reordered widest-first = 54 B.
Visualizer: column-order padding calculator. Column chips (add / remove / move), an 8-byte-row byte map with padding cells, "sort by alignment" button, live tuple length, MAXALIGNed size, rows per page. Algorithm mirrors heap_fill_tuple; validated against `pg_column_size(row(...))`.
Playground: `typlen/typalign` catalog query, pg_column_size per type, bad vs good ordering on real tables (lp_len), float vs numeric, money and rounding, overflow.
Production: a metrics table with 200 M rows where reordering removes padding.
Pitfalls: float for money; `char(n)` padding; assuming reordering always helps (MAXALIGN rounding); money and locale.

## 2. arrays — Arrays
Facts
- Any base/enum/composite/range/domain can be an array element; declared sizes and dimensions are not enforced (arrays).
- Subscripts are 1-based; out-of-range reads return NULL (arrays).
- On-disk ArrayType: varlena header 4, ndim 4, dataoffset 4, elemtype 4, then dims[ndim] and lbound[ndim] (4 B each), an optional null bitmap, data (array.h).
- Measured: `'{1,2,3}'::int4[]` = 36 B in memory, 33 B in a row (1-byte header); `'{1,NULL,3}'` = 40; `'{{1,2},{3,4}}'` = 48; `'{}'` = 16.
- NULL elements take no data space, only a bitmap bit (measured).
- `@>`, `<@`, `&&`, `= ANY`; `array[1,2] || 3`, `array_append(…, NULL)` (functions-array, arrays).
- GIN `array_ops` indexes `@> <@ && =` (gin-builtin-opclasses); `= ANY` is not GIN-indexable.
- "Arrays are not sets"; element searches can mean misdesign (arrays).
- unnest / array_agg / WITH ORDINALITY (functions-array).
Visualizer: two modes. (a) Byte layout of a chosen array value (header fields, dims, lbounds, null bitmap, aligned elements), sizes measured. (b) GIN lookup stepper: rows with tag arrays → key → posting list → intersect for `@>`.
Playground: layout + sizes, operators, unnest/array_agg, GIN with EXPLAIN, normalized alternative.
Production: a tagging feature: GIN on text[] vs join table.
Pitfalls: `= ANY` not using GIN; whole-array rewrite on update; NULL concatenation; 1-based / lbound surprises.

## 3. json-jsonb — JSON vs JSONB
Facts (datatype-json, functions-json, gin-builtin-opclasses)
- json stores exact text; jsonb stores a decomposed binary tree.
- jsonb drops whitespace, sorts object keys (shorter first, then bytewise), keeps the last duplicate key.
- Measured: `{"user":"ana","plan":"pro","user":"ana2",...}` keeps both users in json, only `ana2` in jsonb.
- jsonb can be larger than json for small documents (measured 75 vs 124 B).
- Operators `-> ->> #> #>> @> ? ?| ?&`; `@>` containment semantics.
- `jsonb_ops` indexes keys and values separately (supports `? ?| ?& @> @? @@`); `jsonb_path_ops` hashes each path→value (only `@> @? @@`), smaller.
- `body->>'plan' = 'pro'` cannot use a GIN on body; rewrite as `@>` or add an expression index.
- jsonpath lax (default) vs strict; JSON_TABLE, JSON_EXISTS, JSON_VALUE, JSON_QUERY.
- Large jsonb is TOASTed and compressed like any varlena; any update rewrites the whole value.
Visualizer: side-by-side normalizer (pick a sample doc; animate key reorder, dedup, whitespace), measured sizes; then GIN key extraction for both opclasses.
Playground: normalization, operators, GIN plans, jsonpath lax/strict, JSON_TABLE.

## 4. uuid-v4-v7 — UUIDv4 vs UUIDv7
Facts (datatype-uuid, functions-uuid)
- 128-bit, 16 B; text form is 36 chars (40 B as text measured).
- `gen_random_uuid()` = `uuidv4()`; `uuidv7([shift])`; `uuid_extract_version`, `uuid_extract_timestamp` (v1/v7 only).
- v7 layout: 48-bit Unix ms, 4-bit version, 12-bit sub-ms fraction, 2-bit variant, 62 random bits.
- Values from one session are monotonic (measured: rand_a steps 000, 001, 002 within a millisecond).
- Measured 50k rows: index pages bigint 139, v7 194, v4 271; leaf fill v7 89.8%, v4 64.2%.
Visualizer: live bit-field explorer (generate v4/v7 in browser, decode fields + timestamp) plus a leaf-locality mini-sim with heat map.
Playground: generate/extract, ordering, index size and fill comparison, uuidv7(shift).

## 6. tuple-header — xmin, xmax, ctid, infomask
Facts (storage-page-layout, pageinspect, htup_details.h)
- 23-byte header fields; t_cid overlays t_xvac; t_hoff = 24 without a null bitmap, 24 with ≤ 8 columns + bitmap, 32 with 9–72 columns + bitmap (measured).
- Null bitmap: 1 bit per column, 1 = not null.
- Hint bits XMIN_COMMITTED / XMIN_INVALID / XMAX_COMMITTED / XMAX_INVALID are set by readers.
- FROZEN = XMIN_COMMITTED | XMIN_INVALID.
- Row locks live in xmax with LOCK_ONLY; FOR UPDATE also sets KEYS_UPDATED.
- infomask2 low 11 bits = natts; HOT_UPDATED, HEAP_ONLY_TUPLE, KEYS_UPDATED.
Visualizer: 16-bit infomask/infomask2 grids through 11 captured steps; clickable bits.

## 7. toast — TOAST
Facts (storage-toast, sql-altertable, sql-createtable, runtime-config-client)
- Threshold 2032 B; target 2032 B (toast_tuple_target). Chunks 1996 B, 4 per TOAST page (lp_len 2032).
- 18-byte on-disk pointer: toast relid, value id, raw size, ext size, compression.
- PLAIN / MAIN / EXTERNAL / EXTENDED. pglz default; lz4 needs build support (not in PGlite).
- Measured: 9000 B repetitive text → 122 B inline pglz; 9600 B md5 text → 5 chunks, 18 B pointer.
- toast_tuple_target 4000 keeps a 3040-byte row inline; 256 pushes both columns out of a 2.5 kB row.
- Unchanged TOAST value is reused on UPDATE (same chunk_id).
- Max value 1 GB.

## 8. fsm-vm-forks — Files, forks, FSM, VM
Facts (storage-file-layout, storage-fsm, storage-vm, storage-init, pgfreespacemap, pgvisibility)
- base/<dboid>/<relfilenode>; forks _fsm, _vm, _init; 1 GB segments; TRUNCATE changes the relfilenode (measured 16442 → 16447).
- FSM: one byte per page (32-byte steps), max-tree inside each FSM page; 3-level FSM (24 KB fork measured).
- VM: 2 bits per heap page; set by VACUUM, cleared by any change.
- DELETE clears VM bits immediately; FSM stays stale until VACUUM (measured).
- Unlogged heap init fork is 0 B, btree init fork is 8 KB.
Visualizer: Stepper over captured runs: files panel, page grid (FSM + VM), FSM max-tree with real node values.
