# F5 (`f4`): Practical SQL Patterns — build plan

Audience: practitioners who already write SQL. Every lesson is one pattern: problem → naive solution and why it breaks →
right solution → measured effect (EXPLAIN buffers / row counts captured from PostgreSQL 18). Depth lives elsewhere; each
lesson ends with a "going deeper" pointer to the Internals lesson: m3/* (joins, windows, recursive CTEs, GROUPING SETS),
m4/index-design, m4/explain-analyze, m5/row-locks-skip-locked, m6/full-text-search.

Shared helpers: `app/src/lessons/f4/_ui.tsx` (ResultTable, Sql, Stat, Btn, PlanBox). All numbers in visualizers come from
the capture scripts run against PGlite (PostgreSQL 18.6) with the same schema as the playground.

## 1. pagination — Pagination: OFFSET vs keyset
Facts
1. Rows skipped by OFFSET still have to be computed inside the server, so a large OFFSET is inefficient (queries-limit.html).
2. LIMIT without a unique ORDER BY returns an unpredictable subset; different LIMIT/OFFSET values can produce different plans and orders (queries-limit.html, sql-select.html).
3. `OFFSET start` rows are skipped before LIMIT counting; `LIMIT ALL`/`NULL` = no limit (queries-limit.html).
4. Row-constructor `<`, `>` compare left to right and stop at the first unequal pair: `(a,b) > (x,y)` is lexicographic (functions-comparisons.html).
5. A row comparison against a multicolumn B-tree index whose column order matches is an index condition (indexes-multicolumn.html, functions-comparisons.html).
6. `FETCH FIRST n ROWS ONLY` is the standard spelling; `WITH TIES` needs ORDER BY (sql-select.html).
7. Cursors (`DECLARE … CURSOR`) live only inside a transaction unless `WITH HOLD`, which materializes the rows at commit (sql-declare.html).
8. `count(*)` costs effort proportional to table size; `pg_class.reltuples` is an estimate maintained by VACUUM/ANALYZE (functions-aggregate.html, planner-stats.html).
9. Nulls sort last for ASC; keyset columns should be NOT NULL or handled explicitly (queries-order.html).
10. EXPLAIN ANALYZE reports `Buffers: shared hit=` per node; in 18 ANALYZE implies BUFFERS (using-explain.html).
Visualizer: an index strip of 100 000 entries (bucketed). Slider = page number. OFFSET mode lights every entry read and
discarded, keyset mode seeks to the last seen key and reads 10. Tiles: rows read, shared buffers, time (captured for pages
1/10/100/1 000/5 000). Second toggle "insert while paging": a new row lands on page 1 and OFFSET shows a duplicate while keyset does not.
Playground: `events` 100 k rows, index `(created_at, id)`. Presets: OFFSET page 1 vs deep page; keyset; row comparison vs
the broken `a > x AND b > y`; backward page; total count vs estimate; cursor.
Production: activity feed API timing out on deep pages. Pitfalls: non-unique sort key, wrong comparison expansion, mixed
ASC/DESC directions, exact counts on every request.

## 2. upsert-dedup — Upserts and de-duplication
Facts: ON CONFLICT semantics (arbiter inference, `excluded`, DO UPDATE requires target, WHERE still locks, cardinality
violation, atomic insert-or-update under concurrency) (sql-insert.html). `RETURNING old/new` in 18 (sql-insert.html,
dml-returning.html). MERGE: first matching WHEN clause, cardinality violation, not interchangeable with ON CONFLICT under
concurrency (sql-merge.html). `ctid` changes on UPDATE / VACUUM FULL: use only within one statement (ddl-system-columns.html).
`UNIQUE NULLS NOT DISTINCT` (sql-createtable.html, indexes-unique.html). Expression unique index for case-insensitive
uniqueness (indexes-expressional.html). Sequences consumed by conflicting inserts are not returned (sql-insert/functions-sequence).
Visualizer: two modes. *Upsert*: a batch of incoming rows probes the unique index; each row becomes INSERT, UPDATE, or
skipped (DO UPDATE … WHERE); a duplicate key inside the batch triggers the cardinality error. *Dedup*: rows grouped by
normalized email, `row_number()` labels each, rn > 1 marked for delete, then a unique index locks the door.
Playground: `contacts` with seeded duplicates, `staging` batch. Production: nightly CRM import creating duplicates.

## 3. pivot-reporting — Pivots and reports
Facts: `FILTER (WHERE …)` per aggregate (sql-expressions.html); crosstab source must be ordered, one-arg form fills left
to right and ignores category; two-arg form maps categories (tablefunc.html); GROUPING SETS / ROLLUP and `grouping()`
(queries-table-expressions.html, functions-aggregate.html); `sum` of no rows is NULL (functions-aggregate.html);
`generate_series` over timestamps (functions-srf.html); `lag` (functions-window.html); window aggregate with empty OVER
for percent of total (tutorial-window.html); `date_trunc` (functions-datetime.html).
Visualizer: long rows (month × channel) fold into a pivot grid; toggles: "date spine" (missing month appears as 0 rather
than vanishing), "ROLLUP totals", "% of total", "vs previous month". Clicking a cell highlights its source rows.
Playground: `orders` 3 000 rows over 2026 with a deliberately empty month for one channel.

## 4. gaps-and-islands — Gaps and islands
Facts: `row_number()` numbering within a partition (functions-window.html); date − integer = date (functions-datetime.html);
`lag()` default NULL (functions-window.html); running sum = aggregate with ORDER BY and default frame (functions-window.html);
`generate_series` with EXCEPT for missing values (functions-srf.html, queries-union.html); range types, `&&`, `-|-`,
`range_agg` → multirange (rangetypes.html, functions-range.html, functions-aggregate.html); exclusion constraint
`EXCLUDE USING gist (… WITH &&)` (rangetypes.html).
Visualizer: stepper over a user's activity days: sort → row_number → date − rn → group → island lengths. Mode 2:
sessionization with a timeout slider (lag gap > N minutes → new session; running sum = session id).
Playground: `logins(user_id, day)`, `clicks(user_id, ts)`, `bookings(room, during tstzrange)`.

## 5. hierarchies — Trees and graphs
Facts: recursive CTE evaluation with working table; SEARCH DEPTH/BREADTH FIRST; CYCLE clause (queries-with.html); ltree
labels, `<@`/`@>`, lquery `~`, GiST `gist_ltree_ops`, `nlevel`, `subpath` (ltree.html); B-tree index on parent column
for adjacency lists (indexes-intro.html).
Visualizer: one org tree, three storage models. Click a node to fetch its subtree; adjacency shows recursive iterations
(one index probe per level), ltree shows one range on the path index, closure shows one index lookup on `ancestor`. Move a
subtree: counts of rows each model must rewrite.
Playground: `staff` adjacency (≈ 1 365 nodes, 5 levels), `staff_path` ltree, `staff_closure`.

## 6. search-patterns — Searching text
Facts: LIKE matches whole string; `_`/`%` (functions-matching.html); `text_pattern_ops` for LIKE in non-C locale
(indexes-opclass.html); pg_trgm extraction rules, `similarity`, `%` threshold 0.3, `<->` KNN with GiST not GIN,
`gin_trgm_ops` for LIKE/ILIKE/regex unanchored, patterns with no trigrams → full index scan (pgtrgm.html); full-text
`to_tsvector @@ websearch_to_tsquery`, `ts_rank` (textsearch-controls.html).
Visualizer: type a query; see its padded trigrams, matching candidates with live similarity (same algorithm as pg_trgm),
and a matrix of which index serves which predicate (captured from EXPLAIN).
Playground: `products` 20 k names (en_US collation column) with pg_trgm.

## 7. queues-and-locking — Job queues and concurrency patterns
Facts: SKIP LOCKED semantics and caveat (sql-select.html); row lock taken by FOR UPDATE held to end of transaction
(explicit-locking.html); advisory locks session vs xact, try variants (functions-admin.html, explicit-locking.html);
LISTEN/NOTIFY delivered on commit, between transactions, payload < 8000 bytes (sql-notify.html); optimistic concurrency
via `UPDATE … WHERE version = $v` (row count 0 → retry) (dml-update.html, mvcc); unique index for idempotency keys and
ON CONFLICT DO NOTHING (sql-insert.html); partial index on pending rows (indexes-partial.html).
Visualizer (simulated sessions): three modes on a scripted timeline. Lease queue: claim with SKIP LOCKED, commit lease,
a worker crashes, lease expires, job reclaimed, idempotency key blocks the double charge. Optimistic update: two
sessions read version 7, one wins, one gets 0 rows and retries. Singleton job: `pg_try_advisory_lock`.
Playground: `jobs`, `payments(idempotency_key unique)`, `accounts(version)`.

## 8. performance-checklist — A query performance checklist
Facts: plan anatomy, estimated vs actual rows, `Rows Removed by Filter`, loops multiply (using-explain.html); expression
indexes (indexes-expressional.html); implicit cast prevents index use (typeconv, indexes-types); partial index implication
(indexes-partial.html); pg_stat_statements columns (pgstatstatements.html); `work_mem` and `Sort Method: external merge`
(runtime-config-resource.html, using-explain.html); ANALYZE keeps stats current (planner-stats.html).
Visualizer: EXPLAIN smell detector. Pick one of six captured plans; flagged lines glow with the smell and the rule; toggle
"after fix" for the fixed plan with buffers/time before vs after.
Playground: `users`, `orders` (50 k), pg_stat_statements; presets walk the checklist.
