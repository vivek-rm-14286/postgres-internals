## 1. relational-basics — Tables, rows and your first query
Facts
1. A relational database stores data in **tables**: named collections of **rows**; each row has the same named, typed **columns** (tutorial-concepts).
2. Rows in a table have no guaranteed order; order exists only with ORDER BY (tutorial-concepts, queries-order).
3. Hierarchy: a **cluster** (one server) holds databases; a database holds **schemas**; schemas hold tables; default schema `public` (manage-ag-overview, ddl-schemas).
4. Clients connect to exactly one database per connection; the server process runs SQL and returns rows (tutorial-arch).
5. `SELECT select_list FROM table`; `*` = all columns (tutorial-select, queries-select-lists).
6. Select-list items can be expressions: `price * 1.2` (tutorial-select).
7. `AS` renames an output column; `AS` is optional except before some keywords; an unnamed expression is called `?column?` (queries-select-lists; verified).
8. A table alias `FROM products p` lets you write `p.name` (queries-table-expressions).
9. `--` starts a line comment, `/* */` a block comment (sql-syntax-lexical).
10. A statement ends with `;`; keywords and unquoted names are case-insensitive (sql-syntax-lexical).
11. `numeric(8,2) * 1.2` gives `28.800`: the result scale is the sum of input scales (verified).
12. `current_database()`, `current_schema()`, `current_user` show where you are: `postgres`, `public`, `postgres` (functions-info; verified).
Visualizer: Stepper. Left: nested hierarchy cluster → database → schema → table (active level glows). Right: the products grid with
column/row highlighting, SQL card and animated result table. Steps: hierarchy, table anatomy (row vs column vs cell), `SELECT *`,
column list, expression + alias, table alias, comment and semicolon, client → server round trip. Click any cell to inspect it (row id, column, type, value).
Playground presets: SELECT *, pick columns, expressions with AS, where am I, list tables via information_schema, comments.
Production: an analyst's ad-hoc export uses an explicit column list instead of `SELECT *`.
Pitfalls: relying on row order without ORDER BY; `SELECT *` in application code; double quotes for strings; missing semicolon in psql.

## 2. create-and-insert — Creating tables and inserting rows
Facts
1. `CREATE TABLE name (col type constraints, …)` (ddl-basics, sql-createtable).
2. Common types: `int` (4 bytes), `bigint` (8), `text`, `numeric(p,s)` exact, `boolean`, `date`, `timestamptz` (datatype-*).
3. `PRIMARY KEY` = unique + not null, creates an index (ddl-constraints).
4. `NOT NULL` rejects NULL: error 23502 with "Failing row contains" (verified).
5. `DEFAULT` used when a column is omitted or the keyword DEFAULT is written (ddl-default, dml-insert).
6. `GENERATED ALWAYS AS IDENTITY` auto-numbers; supplying a value errors 428C9 unless `OVERRIDING SYSTEM VALUE`; BY DEFAULT allows overrides (sql-createtable; verified).
7. Failed inserts still consume identity numbers: gaps (functions-sequence; verified id 4 skipped).
8. Multi-row `VALUES (…), (…)` in one statement (dml-insert).
9. `INSERT … SELECT` copies query results (dml-insert).
10. `RETURNING` returns the inserted rows, including generated ids (dml-returning).
11. Single quotes = string literal, double quotes = identifier; `''` escapes a quote; unquoted names fold to lower case (sql-syntax-lexical; verified `"Orders"` vs `orders`).
12. `DROP TABLE [IF EXISTS]` removes table and data (sql-droptable).
13. Bad input for a type errors 22P02 (`'maybe'` for boolean) (verified).
Visualizer: Stepper building `customers` live: CREATE draws header with type/constraint chips; inserts animate rows in, defaults
pulse, identity counter ticks; failing inserts shake red with real error text and burn an id; RETURNING panel.
Playground: create, insert one + RETURNING, multi-row, defaults, errors via a `try_sql` helper, INSERT … SELECT, quoting, DROP.
Production: signup service inserting and getting the id back in one round trip with RETURNING.
Pitfalls: supplying ids manually with identity; double quotes for strings; mixed-case quoted identifiers; float for money.
Going deeper: I2 "Primitive types, alignment and padding".

## 3. filter-and-sort — Filtering and sorting
Facts
1. WHERE keeps rows whose condition is **true**; false and NULL are both dropped (queries-table-expressions).
2. Comparison `= <> != < > <= >=` (functions-comparison).
3. Precedence: NOT > AND > OR; use parentheses (sql-syntax-lexical operator precedence).
4. `IN (list)`, `BETWEEN a AND b` inclusive both ends (functions-comparison).
5. `LIKE`: `%` any run, `_` one char; case-sensitive; `ILIKE` case-insensitive (PG extension) (functions-matching).
6. `x = NULL` is never true; use `IS NULL` / `IS NOT NULL` (functions-comparison; verified 0 rows).
7. Three-valued logic: NULL AND false = false, NULL OR true = true, NOT NULL = NULL (functions-logical).
8. `x NOT IN (…, NULL)` is never true (functions-subquery / comparisons).
9. ORDER BY multiple keys, ASC default, DESC; NULLs sort as larger: last in ASC, first in DESC; NULLS FIRST/LAST override (queries-order).
10. LIMIT n / OFFSET m; without ORDER BY the subset is unpredictable (queries-limit).
11. `FETCH FIRST n ROWS WITH TIES` also returns rows tying the last; needs ORDER BY (sql-select; verified 4 rows).
12. `DISTINCT` removes duplicate rows; NULLs count as equal for DISTINCT (queries-select-lists).
Visualizer: live filter lab. Choose a WHERE condition; each row shows its evaluated value (true/false/NULL chip); rows not true fade.
Then sort key/direction/NULLS and a LIMIT slider re-order with layout animations. Side panel: three-valued truth table (click an operator).
Playground: comparison, AND/OR precedence, IN/BETWEEN, LIKE/ILIKE, NULL traps, ORDER BY NULLS, LIMIT/OFFSET/WITH TIES, DISTINCT.
Production: "low stock" alert missing items whose stock is NULL.
Pitfalls: `= NULL`; OR without parentheses; NOT IN with NULL; LIMIT without ORDER BY.
Going deeper: I3 "Designing indexes".

## 4. aggregate-basics — Counting, summing and grouping
Facts
1. Aggregates compute one result from many rows: count, sum, avg, min, max (tutorial-agg, functions-aggregate).
2. `count(*)` counts rows; `count(col)` counts non-NULL values (verified kitchen 3 vs 2).
3. All aggregates except count ignore NULL inputs and return NULL for zero rows (functions-aggregate).
4. GROUP BY forms one group per distinct key; every select-list column must be grouped or aggregated: error 42803 (queries-table-expressions; verified).
5. WHERE filters rows before grouping; HAVING filters groups after (tutorial-agg).
6. Aggregates are not allowed in WHERE (42803) (verified).
7. Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT (sql-select).
8. So ORDER BY may use an output alias, but WHERE and HAVING cannot (sql-select).
9. `avg(numeric)` returns many decimals; `round(x, 2)` for presentation (functions-math).
10. Group by an expression, such as `price >= 20` (queries-table-expressions).
11. NULL group keys form one group (queries-table-expressions).
Visualizer: pipeline Stepper over one query (WHERE price < 100, GROUP BY category, HAVING count(*) >= 3, ORDER BY avg DESC, LIMIT 1):
stage rail lights up; rows fade out at WHERE, fly into buckets at GROUP BY, buckets collapse to one row with aggregates, HAVING strikes office,
SELECT computes columns, ORDER BY swaps, LIMIT cuts. Result home | 3 | 33.00.
Playground: count(*) vs count(col), sum/avg/min/max, GROUP BY, the 42803 error, HAVING vs WHERE, group by expression, the pipeline query.
Production: daily sales summary per category for a dashboard.
Pitfalls: non-grouped column; count(col) where count(*) meant; aggregate in WHERE; sum of nothing is NULL.
Going deeper: F4 "Aggregates, FILTER and GROUPING SETS" and I3 "From SQL text to rows".

## 5. change-data-safely — Updating and deleting safely
Facts
1. `UPDATE t SET col = expr WHERE …` changes matching rows; without WHERE, every row (dml-update).
2. `DELETE FROM t WHERE …`; without WHERE, every row (dml-delete).
3. Command tag reports rows affected: `UPDATE 3`, `DELETE 1` (sql-update, sql-delete).
4. SET expressions see the old row values (`price = price * 1.1`) (sql-update).
5. `RETURNING` shows changed rows (dml-returning).
6. Outside BEGIN, each statement commits by itself (autocommit) (tutorial-transactions).
7. `BEGIN … COMMIT` makes a group atomic; `ROLLBACK` undoes everything since BEGIN (tutorial-transactions).
8. After an error inside a transaction, every statement fails (25P02) until ROLLBACK (tutorial-transactions; verified).
9. `TRUNCATE` empties a table fast, takes ACCESS EXCLUSIVE lock, fires no ON DELETE triggers, can `RESTART IDENTITY`; it is transaction-safe (sql-truncate).
10. DELETE leaves dead rows for VACUUM; TRUNCATE reclaims space immediately (sql-truncate, routine-vacuuming).
11. A SELECT with the same WHERE previews exactly the rows an UPDATE will touch (same snapshot logic for a single session).
Visualizer: two modes (safe workflow / missing WHERE). Steps: preview SELECT highlights rows; BEGIN; UPDATE … RETURNING changes cells
(old → new); check count; COMMIT (rows turn solid) or ROLLBACK (values spring back). Transaction badge and "what others see" lane.
Playground: preview, BEGIN/UPDATE/ROLLBACK, BEGIN/UPDATE/COMMIT, DELETE RETURNING, the missing WHERE caught by rollback, aborted transaction, TRUNCATE vs DELETE.
Production: a support engineer fixing a mispriced category with the preview → transaction → check → commit routine.
Pitfalls: missing WHERE; forgetting COMMIT leaves a transaction open; aborted transaction errors; TRUNCATE locks and skips triggers.
Going deeper: I4 "ACID and transactions" and F4 "INSERT, UPDATE, DELETE, MERGE: what really happens".
