# E3 — Distributed PostgreSQL (plan)

Track: ecosystem. Folder `app/src/lessons/e3/`. Shared helpers: `_ui.tsx` (buttons, stats, `hashint4` port verified
against PGlite on 2053 values, `TRY_SQL` setup snippet). Facts below come from
`research/X-distributed-postgres.md` (primary docs: Citus 14, YugabyteDB, Spock 5, PGD 6.5, Patroni, Neon, Aurora) and the
PG 18 docs. The playground never pretends an extension is installed: it runs native PG 18 stand-ins on one node and says so.

Global playground rules: no statement may wait on a lock (lock_timeout does not fire in the browser). Prepared
transactions are always resolved in the same preset; locked rows are probed only with `FOR UPDATE NOWAIT` (inside
`try_sql`) or `SKIP LOCKED`. No `CREATE SUBSCRIPTION`, no logical decoding.

## 1. why-distribute — Why and how to distribute PostgreSQL
Key facts
1. PostgreSQL is single-node: one data directory, one WAL stream; it ships replication and FDWs but no sharding, no distributed txn manager, no automatic failover (different-replication-solutions, warm-standby-failover).
2. Three mechanisms: replication (copies), distribution (parts), decentralization (storage vs compute).
3. The protocol is synchronous: 20 ms per transaction = 50 txn/s per session (computed: 1000/20).
4. Read replicas: writes on one primary; reads scale; no read-your-writes / monotonic reads when async (high-availability).
5. Shared storage: Aurora 10 GB protection groups, 6 copies across 3 AZs, write quorum 4 of 6, up to 15 replicas; Neon compute → safekeepers (Paxos quorum) → pageserver → object storage.
6. Sharding (Citus): coordinator + workers, hash by distribution column, 32 shards default.
7. Distributed SQL (YugabyteDB): tablets, Raft per tablet, a leader per tablet, re-election in about 2 s.
8. Multi-master (PGD, Spock): every node writable, async logical replication, conflicts resolved after commit.
9. CAP: on a partition choose consistency or availability; Raft/Paxos systems are CP, async multi-master is AP.
10. PACELC: else latency vs consistency; `synchronous_commit` levels and `synchronous_standby_names` FIRST/ANY are that knob (runtime-config-replication, warm-standby).
Visualizer: architecture explorer. Segmented over 5 architectures; one SVG with client, nodes and storage; buttons
"Send a write" (viz-next), "Send a read", "Fail a node" (per architecture: primary / storage node / worker / tablet leader / one site).
Animated packets along hop paths; a fact panel (writes on, reads from, consistency, on failure, CAP). Second panel:
latency budget sliders (RTT, round trips per txn, sessions) → TPS per session and ceiling.
Playground: native building blocks. Presets: WAL stream bytes per write; commit knobs; a physical slot; hash partitions as shards; a publication; latency maths in SQL.
Production: a SaaS that wants "to go distributed" measures first and picks replicas + HA. Pitfalls: replica read-your-writes, single sync standby stalls commits, distributing before batching/pooling, "cluster" ambiguity.

## 2. sharding-citus — Sharding with Citus
Key facts: coordinator/workers, MX mode (Citus 11+); `create_distributed_table(table, column, colocate_with => 'default')`;
`citus.shard_count` 32; shard `<table>_<shardid>`; `pg_dist_shard` shardminvalue/shardmaxvalue over int32 hash tokens
(2^32/32 = 134,217,728 per shard); colocation by same type + shard count; reference tables (one shard on every worker,
2PC writes); schema-based sharding (12.0, `citus_schema_distribute`, ~1–10k tenants vs row-based ~1–1M+);
PK/UNIQUE must include the distribution column; FKs: colocated incl. dist column, or → reference; not reference → distributed;
changing the dist column type is refused. Sources: ddl-partitioning (stand-in), ddl-constraints.
Visualizer: shard map. 32 shards coloured by worker (2/3/4 workers), type a company id → hashint4 token → shard →
worker; tables companies/campaigns/ads colocated (same shard index, same worker) vs `colocate_with => 'none'`; reference
table copies on every worker; mode distributed / reference / schema-based. viz-next = "Route next key".
Playground: `pg_dist_shard_sim` built with hashint4; companies/campaigns/ads hash-partitioned 4 ways (colocated
stand-in); unique and FK rules via `try_sql`; schema-per-tenant.

## 3. distributed-queries — Distributed query execution
Key facts: router (fast path) when the filter pins the dist column; multi-shard = one task per shard, merged on the
coordinator; `Custom Scan (Citus Adaptive)`, `Task Count: 32`, `Tasks Shown: One of 32`; aggregates split
(avg → sum + count per shard); push-pull recursive planning with `read_intermediate_result`, `citus.max_intermediate_result_size` 1 GB;
repartition joins off by default (`citus.enable_repartition_joins`); `citus.max_adaptive_executor_pool_size` 16;
rebalancer `citus_rebalance_start()` (by_disk_size default, background), `get_rebalance_table_shards_plan()`,
`citus_move_shard_placement`, `shard_transfer_mode` auto/force_logical/block_writes; `isolate_tenant_to_new_shard`.
Visualizer: Stepper per query type (router / fan-out aggregate / colocated join / repartition join / rebalance), coordinator
+ 3 workers, tasks fly out, partial results fly back with real numbers from the stand-in data; EXPLAIN panel.
Playground: partition pruning, Append fan-out, Partial/Finalize aggregate and manual sum/count, partitionwise join,
non-colocated join, detach/attach and split (modulus 4 → 8).

## 4. distributed-transactions — Distributed transactions and consistency
Key facts: PREPARE TRANSACTION / COMMIT PREPARED / ROLLBACK PREPARED, GID < 200 bytes, `max_prepared_transactions` 0 disables,
prepared state on disk, any session can finish it, holds locks and xmin (sql-prepare-transaction, view-pg-prepared-xacts);
postgres_fdw has no 2PC (postgres-fdw); 2PC blocks when the coordinator dies after PREPARE; HLC = (physical, logical);
YugabyteDB intents + status tablet; isolation mapping; sequences per node; uniqueness/FKs across shards.
Visualizer: tabs: 2PC Stepper (commit / vote no / coordinator dies → in-doubt → recovery) with lanes and
pg_prepared_xacts; HLC lab (two clocks with skew, send/receive); "what changes" matrix.
Playground config: `max_prepared_transactions = 10`, `track_commit_timestamp = on`. Two schemas as two participants.

## 5. distributed-sql-multimaster — Distributed SQL and multi-master
Key facts: YugabyteDB YQL over DocDB (RocksDB), YB-TServer/YB-Master, tablets with Raft, hash 0x0000–0xFFFF, first PK column hashed,
`SPLIT INTO n TABLETS`; v2025.1 rebased on PG 15; RC only with `yb_enable_read_committed_isolation` (default for new
universes from v2025.2), wait queues default since v2024.1. PGD 6.5: commit scopes, conflict types and resolvers,
global sequences; Spock 5: `spock.conflict_resolution` error / apply_remote / keep_local / last_update_wins,
delta-apply, FKs not enforced during apply; PG 18 conflict types (`confl_*`) (logical-replication-conflicts).
Visualizer: tabs: Raft (3 nodes × 3 tablets, write → majority, fail/recover nodes, elections); conflict lab
(two nodes, overwrite or increment, skew slider, 5 resolution modes, converge/diverge/lost update).
Playground: two schemas as two nodes with commit timestamps, a trigger-built change log, LUW and delta resolution in SQL.

## 6. ha-clusters — High-availability clusters in practice
Key facts: Patroni leader key in a DCS (etcd/etcd3/Consul/ZooKeeper/Kubernetes); ttl 30 / loop_wait 10 / retry_timeout 10,
`loop_wait + 2*retry_timeout <= ttl`; `maximum_lag_on_failover`; REST `/primary` 200 only on the leader, `/replica`;
HAProxy `option httpchk`, `inter 3s fall 3 rise 2`; `synchronous_mode`; `pg_rewind`; STONITH (warm-standby-failover);
`pg_promote()`; sync replication `FIRST`/`ANY` (warm-standby).
Visualizer: Stepper generated from ttl/loop_wait/retry_timeout sliders; scenarios crash / partition (fencing) /
switchover; lanes for pg1–pg3, etcd leader key with TTL bar, HAProxy routes; rule check turns red on split-brain window.
Playground: role and lag queries, slots per member, per-transaction sync commit, settings contexts, timeline/WAL file, the timing rule in SQL.
