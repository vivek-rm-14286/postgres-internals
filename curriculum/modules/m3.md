## 1. dml-lifecycle — INSERT, UPDATE, DELETE, MERGE: what really happens
Facts
1. UPDATE writes a new row version and stamps the old one's `xmax`; DELETE only sets `xmax` (storage-hot, dml-update).
2. `RETURNING` works on INSERT, UPDATE, DELETE and MERGE; unqualified columns are NEW for INSERT/UPDATE, OLD for DELETE (dml-returning).
3. PG18: `old.*` / `new.*` in RETURNING; old is NULL for INSERT, new is NULL for DELETE; `RETURNING WITH (OLD AS o, NEW AS n)` renames (dml-returning, sql-update).
4. ON CONFLICT DO UPDATE: old values are non-NULL for conflicting rows (dml-returning).
5. Arbiter = every unique index whose columns exactly match the conflict target; DO UPDATE requires a target; DO NOTHING does not (sql-insert).
6. `EXCLUDED` is the proposed row; it is usable in SET/WHERE of DO UPDATE only, not in RETURNING (sql-insert; verified error).
7. DO UPDATE may not touch the same row twice in one command: cardinality violation (sql-insert).
8. INSERT … ON CONFLICT computes nextval before detecting the conflict, so sequences gap even without aborts (functions-sequence).
9. nextval is never rolled back; a failed INSERT still burns a value (functions-sequence; verified 5→6).
10. MERGE: each candidate row gets one status (MATCHED / NOT MATCHED [BY TARGET] / NOT MATCHED BY SOURCE); first true WHEN wins (sql-merge).
11. MERGE raises cardinality violation if a target row joins several source rows; UPDATE … FROM silently picks one (sql-merge, sql-update).
12. `merge_action()` only valid in MERGE RETURNING (functions-merge-support).
13. Command tags: `INSERT 0 n`, `UPDATE n` counts matched rows even if unchanged, `MERGE n` (sql-insert, sql-update, sql-merge).
14. Each statement outside BEGIN is its own transaction (one xid per statement) (tutorial-transactions).
15. COPY is the bulk path; `ON_ERROR ignore`, `REJECT_LIMIT` (18) (sql-copy).
Visualizer: Stepper over 8 captured statements on `inventory(id identity, sku PK, qty CHECK >= 0)`: line-pointer list with xmin/xmax per version (live/dead/new/lock-only), a RETURNING panel, a sequence counter with burned ids, command tag. Proves: versions not overwrite; RETURNING old/new; upsert gap; MERGE one xid for three actions.
Playground: inventory + delivery + pageinspect; presets: versions, RETURNING old/new, upsert + gap, MERGE + merge_action, cardinality violation, data-modifying CTE move.
Production: idempotent stock ingestion with upsert from a staging table; MERGE with NOT MATCHED BY SOURCE for sync.
Pitfalls: gaps assumed gapless invoice numbers; upsert batch with duplicate keys; UPDATE … FROM multi-match; mass UPDATE bloat (batch).

## 2. joins — Joins, visualized
Facts: CROSS = N×M; INNER pairs where ON is true; LEFT adds unmatched left NULL-extended; RIGHT mirrored; FULL both; ON filters before the join, WHERE after (queries-table-expressions); USING merges columns, NATURAL joins on all same-named columns and becomes CROSS JOIN with none; NULL = NULL is not true so NULL keys never match; EXISTS = semi-join, NOT EXISTS = anti-join (functions-subquery); JOIN binds tighter than comma; alias hides table name; self-join needs aliases.
Visualizer: teams (4) × players (5, two NULL team_id). Join-type toggle (INNER/LEFT/RIGHT/FULL/CROSS/SEMI/ANTI) and filter toggle (none / `AND p.active` in ON / `WHERE p.active`). Step through each left row: comparisons drawn as lines, result rows appear, NULL-extended rows highlighted. Counts: inner 3, left 5, right 5, full 7, cross 20, semi 2, anti 2; ON-filter 4 vs WHERE-filter 2.
Playground: teams/players/countries; presets per join, ON vs WHERE, NATURAL trap, self-join manager, anti-join plan.
Production: "customers without orders this month" report that silently dropped rows when filter moved to WHERE.
Pitfalls: WHERE on nullable side; NATURAL JOIN new column; fan-out double counting; NULL keys.

## 3. subqueries — scalar, IN, EXISTS, ANY/ALL
Facts (functions-subquery, functions-comparisons): EXISTS true iff ≥1 row, never NULL, stops early; IN = `= ANY`; NOT IN = `<> ALL`; NOT IN returns NULL when no match and the list has a NULL; empty subquery: IN false, NOT IN true, ALL true, ANY false; scalar subquery: >1 row is an error, 0 rows gives NULL; correlated subqueries re-run per outer row (SubPlan); planner turns IN/EXISTS into Semi Join and NOT EXISTS into Anti Join, but NOT IN stays a hashed SubPlan filter.
Verified: 4,996-row customers, 3 refunds incl. NULL → NOT IN returns 0 rows, NOT EXISTS 4285.
Visualizer: outer customers 1..4, subquery `refunds.customer_id` = {2, 4, NULL} with NULL toggle; operator toggle (NOT IN / NOT EXISTS / IN / EXISTS); per-row step shows expansion `1 <> 2 AND 1 <> 4 AND 1 <> NULL` → three-valued result → kept/dropped, plus the captured plan shape.
Production: suppression list query returning zero rows after one NULL row landed.

## 4. ctes — inlined vs MATERIALIZED
Facts (queries-with, sql-select): non-recursive, side-effect-free CTE referenced once is folded; referenced twice it is materialized; MATERIALIZED forces a fence; NOT MATERIALIZED forces folding; volatile functions prevent folding; before v12 always a fence; data-modifying CTEs run once to completion, share one snapshot, see each other only via RETURNING; DML in WITH only at top level; same row modified twice unsupported.
Captured on orders(20,000 rows, index on customer_id): inline → Bitmap Index Scan, 40 rows, shared hit=42; MATERIALIZED → CTE Scan, Seq Scan 20,000 rows, Rows Removed 19,960, 1066kB, hit=128; double reference → CTE Scan ×2; NOT MATERIALIZED → index scan on one side.
Visualizer: Stepper over 5 plan trees (plus the data-modifying CTE snapshot step) with rows-per-node bars.

## 5. recursive-ctes
Facts (queries-with): non-recursive term UNION [ALL] recursive term; iterative algorithm with working and intermediate tables; UNION discards duplicates of any previous row; stops when the working table is empty; breadth-first output is an implementation detail; SEARCH DEPTH/BREADTH FIRST BY … SET col; CYCLE col SET is_cycle USING path; LIMIT in parent only for testing; only one self-reference; recursive DML not allowed.
Verified: org chart under Raj → 6 rows, depth 0..3; routes A→B→C→A, C→D: UNION (node only) → A,B,C,D; UNION ALL + hops → infinite; CYCLE → 5 rows, A at hop 3 marked.
Visualizer: mode toggle tree / graph-UNION ALL / graph-UNION / graph-CYCLE; steps = iterations showing working table, intermediate table, result, highlighted nodes.

## 6. window-functions
Facts (functions-window, sql-select, sql-expressions): window functions run after WHERE/GROUP BY/HAVING; do not collapse rows; peers = equal ORDER BY values; default frame RANGE UNBOUNDED PRECEDING to CURRENT ROW (last peer); without ORDER BY whole partition; ROWS/RANGE/GROUPS; RANGE offset needs exactly one ORDER BY column (verified error); EXCLUDE CURRENT ROW/GROUP/TIES; first/last/nth_value see the frame; rank functions agree for peers; WINDOW clause.
Verified on 11 products: running sum with default frame 3550 for all three 700 rows; Laptop last_value default = Sony VAIO for both peers.
Visualizer: frame explorer: click a row, choose mode, start/end bounds and offsets, exclusion, optional partition; frame and peers highlighted; live sum/count/first/last/nth values and rank columns.

## 7. lateral
Facts (queries-table-expressions, sql-select): LATERAL subquery can reference earlier FROM items; per-row evaluation; functions in FROM are implicitly lateral; LEFT JOIN LATERAL … ON true keeps rows with empty results; WITH ORDINALITY adds bigint ordinality; RIGHT JOIN LATERAL cannot reference left; plan = Nested Loop.
Verified: without LATERAL → "invalid reference to FROM-clause entry for table a"; CROSS JOIN LATERAL top-2 → 5 rows, LEFT JOIN LATERAL → 6 rows with Umbrella NULL.
Visualizer: outer row loop; for each account run the subquery with `a.id` bound, show its result, append to output; toggle CROSS vs LEFT and limit 1/2/3.

## 8. aggregates-grouping
Facts (functions-aggregate, queries-table-expressions): aggregates except count return NULL on empty input; count(*) counts rows, count(col) non-null; FILTER; ordered-set aggregates (percentile_cont interpolates, percentile_disc picks, mode); GROUPING SETS ≡ UNION ALL of groupings; ROLLUP = prefixes, CUBE = power set; grouping() bitmask rightmost = LSB; HAVING filters groups; aggregates cannot be in WHERE; DISTINCT ON keeps first row per key in ORDER BY order.
Verified: items_sold with ('Baz', NULL, 8) → CUBE has two `(NULL, NULL)` rows: 8 (g=2) and 58 (g=3).
Visualizer: grouping-set builder: ROLLUP / CUBE / custom sets toggles, lattice of sets, step through each set showing which input rows fold into which output rows, grouping() bits.
